# DataDignity — Cryptographic Key Lifecycle Specification

This document provides the formal implementation-oriented specification for DataDignity's key hierarchy, Data Encryption Key (DEK) lifecycle, beneficiary public-key wrapping, fingerprint verification, revocation, and key rotation workflows.

---

## 1. Purpose and Scope

The purpose of this specification is to define the exact cryptographic standards, key management flows, and zero-knowledge boundaries for DataDignity prior to production cryptographic implementation (Phase 2). 

This specification governs all cryptographic key generation, payload encryption, key wrapping, beneficiary onboarding, key rotation, and recovery mechanisms across the client runtime, backend API, and database layers.

---

## 2. Key Hierarchy

DataDignity enforces a multi-tier cryptographic key hierarchy to ensure zero-knowledge confidentiality and passphrase-independent beneficiary recovery.

```
+-------------------------------------------------------------------------------+
| 1. USER MASTER PASSPHRASE                                                    |
|    (Secret known only to the user; never leaves client browser)                |
+---------------------------------------+---------------------------------------+
                                        | PBKDF2 / Argon2id (Salt + Iterations)
                                        v
+-------------------------------------------------------------------------------+
| 2. MASTER KEY ENCRYPTING KEY (KEK)                                           |
|    (Client-side symmetric key used to encrypt user's copy of DEKs)           |
+---------------------------------------+---------------------------------------+
                                        |
       +--------------------------------+--------------------------------+
       |                                                                 |
       v                                                                 v
+---------------------------------------+ +---------------------------------------+
| 3. DATA ENCRYPTION KEY (DEK)          | | 4. BENEFICIARY PUBLIC / PRIVATE KEY   |
|    (Random 256-bit AES-GCM per-asset  | |    (Asymmetric pair generated on     |
|     symmetric encryption key)         | |     beneficiary client device)        |
+-------------------+-------------------+ +-------------------+-------------------+
                    |                                         |
                    +--------------------+--------------------+
                                         | Asymmetric Key Wrapping
                                         v
+-------------------------------------------------------------------------------+
| 5. WRAPPED DEK ENVELOPE                                                       |
|    (DEK encrypted with Beneficiary Public Key for zero-knowledge recovery)    |
+-------------------------------------------------------------------------------+
```

### Key Definitions

1. **User Master Passphrase**: User-entered passphrase used exclusively on the client to derive the Master KEK.
2. **Master Key Encrypting Key (KEK)**: Symmetric key derived client-side via PBKDF2 SHA-256 (100,000+ iterations) to wrap the DEK for the user's active session access.
3. **Data Encryption Key (DEK)**: Cryptographically random 256-bit symmetric key (`AES-GCM-256`) generated per vault asset to encrypt payload contents.
4. **Beneficiary Key Pair**: Asymmetric key pair generated by each beneficiary on their own client device. The Public Key is registered with DataDignity for DEK wrapping; the Private Key remains secret on the beneficiary's device for DEK unwrapping upon trigger.
5. **Wrapped DEK Envelope**: Ciphertext container holding the DEK encrypted under a verified beneficiary's public key.

---

## 3. DEK Generation

- **Generation Location**: Strictly within the user's client browser runtime using Web Crypto API.
- **Randomness Requirement**: Generated using cryptographically secure random number generators (`window.crypto.getRandomValues()`).
- **Algorithm & Size**: 256-bit (32 bytes) symmetric key for `AES-GCM-256`.
- **Scope**: Unique DEK generated per individual vault entry asset.
- **What Leaves the Browser**: Wrapped DEK envelopes (encrypted with beneficiary public keys or Master KEK).
- **What NEVER Leaves the Browser as Plaintext**: Raw unwrapped DEK byte arrays.

---

## 4. Data Encryption

Vault payloads are encrypted using AES-GCM (Galois/Counter Mode) to ensure both confidentiality and authenticated integrity.

- **Algorithm**: `AES-GCM-256` via Web Crypto API (`SubtleCrypto.encrypt()`).
- **Initialization Vector (IV)**: 96-bit (12 bytes) cryptographically random IV generated per encryption operation via `window.crypto.getRandomValues()`.
- **IV Uniqueness**: A new random 96-bit IV is generated for every single payload encryption. IV reuse with the same DEK is strictly forbidden.
- **Authenticated Integrity**: 128-bit authentication tag automatically appended by AES-GCM to prevent ciphertext modification or tampering.
- **Storage Payload Format**: Server stores stringified JSON ciphertext envelopes containing `{ ciphertext, iv, auth_tag, dek_version }`.
- **Plaintext Handling**: Plaintext buffers are held in temporary memory during encryption and immediately released to garbage collection; plaintext is never stored in persistent browser storage or transmitted to backend servers.

---

## 5. Beneficiary Key Generation & Registration

- **Key Pair Type**: Asymmetric key pair generated on the beneficiary's local device or hardware security module.
- **Generation Location**: Beneficiary client browser runtime using Web Crypto API (`SubtleCrypto.generateKey()`).
- **Private Key Confidentiality**: Beneficiary Private Key is encrypted locally with a beneficiary passphrase or stored in protected WebAuthn/IndexedDB storage. The server **NEVER** receives, transmits, or stores beneficiary private keys.
- **Public Key Export & Format**: Exported in standard SubjectPublicKeyInfo (SPKI) format (PEM or JWK structure).
- **Public Key Registration**: Beneficiary public key is transmitted over TLS to the backend database along with an out-of-band SHA-256 fingerprint.

---

## 6. DEK Wrapping Architecture

DEK wrapping enables passphrase-independent recovery: beneficiaries can unwrap asset DEKs using their own private keys without needing the unavailable user's passphrase.

- **Wrapping Trigger**: Occurs client-side during asset creation, asset editing, or when assigning a verified beneficiary to an asset.
- **Wrapping Key**: Beneficiary's verified Public Key.
- **Unwrapping Key**: Beneficiary's Private Key (executed strictly client-side on beneficiary device upon protocol trigger).
- **Multiple Beneficiaries**: If an asset is assigned to $N$ beneficiaries, the client generates $N$ distinct wrapped DEK envelopes:
  $$\text{WrappedDEK}_i = \text{Encrypt}_{\text{PubKey}_i}(\text{DEK})$$
- **Passphrase Independence**: Beneficiaries use $\text{PrivKey}_i$ to recover $\text{DEK}$, granting access to the asset ciphertext without knowledge of the user's master passphrase.

> [!IMPORTANT]
> **DECISION REQUIRED — Asymmetric Key Wrapping Standard**:
> The project must finalize between two Web Crypto API asymmetric key wrapping standards:
> 1. **RSA-OAEP (4096-bit)**: Native Web Crypto support, direct key wrapping, larger key/ciphertext size (~512 bytes per wrapped DEK).
> 2. **ECDH-ES (P-384 / Curve25519) + AES-KW**: Smaller key size, ephemeral-static key agreement deriving an AES key-wrapping key.
> *Status*: `DECISION REQUIRED`. RSA-OAEP-4096 is recommended for initial implementation due to baseline Web Crypto browser compatibility.

## 7. Beneficiary Fingerprint Verification

To protect against Man-in-the-Middle (MITM) key substitution attacks, beneficiary public keys require out-of-band fingerprint verification before being trusted for DEK wrapping.

```
Beneficiary Client                           Active User Client
+--------------------+                       +--------------------+
| Exports Public Key |                       | Fetches Public Key |
+---------+----------+                       +---------+----------+
          |                                            |
          v                                            v
| Computes SHA-256   |                       | Computes SHA-256   |
| Fingerprint        |                       | Fingerprint        |
+---------+----------+                       +---------+----------+
          |                                            |
          +---------> Out-of-Band Comparison <---------+
                      (In person, Signal, Phone)
                                   |
                      Match Confirmed in UI
                                   |
                                   v
                      Key Status -> VERIFIED
                      Eligible for DEK Wrapping
```

1. **Fingerprint Computation**: SHA-256 hash computed over the raw SPKI DER bytes of the public key:
   $$\text{Fingerprint} = \text{SHA-256}(\text{SPKI\_Bytes})$$
2. **Display Format**: Rendered in UI as 8 groups of 4 hexadecimal characters separated by colons (e.g., `4A8F:9C12:3B7E:8801:D4F5:112A:908C:E543`).
3. **Out-of-Band Verification**: The user and beneficiary compare fingerprints through a trusted out-of-band channel (e.g. secure voice call, in-person check, or encrypted messaging).
4. **Trust State Transition**: Public key status defaults to `UNVERIFIED`. The client application will **NOT** wrap DEKs for unverified public keys. Once verified by the user, status advances to `VERIFIED`.
5. **Failed Verification**: If fingerprints do not match, the key is marked `REJECTED` and purged from the tenant's beneficiary list.

---

## 8. Beneficiary Key Loss and Recovery

- **Lost Private Key Scenario**: If a beneficiary loses their device or private key, they cannot unwrap existing wrapped DEKs delivered upon trigger.
- **Recovery & Re-Registration Workflow**:
  1. Beneficiary generates a new asymmetric key pair on their new device.
  2. Beneficiary submits the new public key for onboarding.
  3. User completes out-of-band fingerprint verification for the new public key.
  4. Active user's client re-wraps the asset DEKs using the new verified public key.
  5. Old public key and wrapped DEK entries are marked `DEPRECIATED` and deleted.
- **Shamir Secret Sharing**: Shamir Secret Sharing is **NOT** used in DataDignity. Recovery is achieved via direct asymmetric key wrapping per assigned beneficiary.

---

## 9. Beneficiary Revocation and DEK Rotation

Logical database deletion of a beneficiary is cryptographically insufficient because a revoked beneficiary retains copies of previously wrapped DEKs. True revocation requires DEK Rotation.

### Revocation Protocol Flow

```
User Action: Revoke Beneficiary B2
  │
  ├── 1. Mark B2 as REVOKED in database (Logical Revocation)
  │
  ├── 2. Fetch active payload ciphertext (encrypted with DEK_old)
  │
  ├── 3. Decrypt payload using DEK_old in user browser memory
  │
  ├── 4. Generate NEW random DEK_new (256-bit AES-GCM)
  │
  ├── 5. Re-encrypt payload with DEK_new -> Ciphertext_new
  │
  ├── 6. Wrap DEK_new ONLY for remaining active beneficiaries (B1, B3...)
  │
  ├── 7. Discard DEK_old and B2's wrapped DEK copy
  │
  └── 8. Commit Ciphertext_new and new Wrapped DEKs to Database (Cryptographic Revocation)
```

- **Cryptographic Security Guarantee**: Revoked beneficiary $B_2$ possesses only $\text{WrappedDEK}_{\text{old}}$, which corresponds to $\text{DEK}_{\text{old}}$. Because the active payload is now encrypted with $\text{DEK}_{\text{new}}$, $B_2$ cannot decrypt current or future vault data even if they possess historical ciphertext copies.

---

## 10. Key Rotation Specifications

### Rotation Triggers
1. Beneficiary revocation.
2. Beneficiary key replacement (e.g. after device loss).
3. Suspected key or passkey compromise.
4. Manual user-initiated security refresh.

### Rotation Mechanics
- **Replacement Key**: Client generates a fresh 256-bit AES-GCM key (`DEK_new`).
- **Re-encryption**: Payload decrypted in memory with `DEK_old` and re-encrypted with `DEK_new`.
- **Re-wrapping**: `DEK_new` wrapped using public keys of all current `VERIFIED` beneficiaries.
- **Atomicity & Interruption Recovery**: Server updates ciphertext and wrapped DEK envelopes in a single atomic database transaction (`PRISMA $transaction`). If rotation is interrupted before commit, the database retains `DEK_old` and ciphertext state, keeping the asset in `SAFE HOLD` until rotation completes.

## 11. Server Visibility Matrix

To enforce the Zero-Knowledge Trust Boundary defined in `THREAT_MODEL.md`, backend servers and database storage strictly segregate allowed metadata from forbidden secrets.

### ALLOWED Server-Side Material
- Ciphertext asset payloads (`AES-GCM-256`)
- Initialization Vectors (IVs) and AES-GCM authentication tags
- Wrapped DEK envelopes (`WrappedDEK_i` ciphertext)
- Beneficiary Public Keys (SPKI PEM/JWK)
- Public Key Fingerprints (SHA-256 hashes)
- PBKDF2 salts and iteration parameters
- DEK version counters and rotation timestamps
- Beneficiary verification flags (`UNVERIFIED`, `VERIFIED`, `REVOKED`)

### FORBIDDEN Server-Side Material
- Raw unwrapped Data Encryption Keys (DEKs)
- Plaintext asset contents
- User Master Passphrases
- Master Key Encrypting Keys (KEKs)
- Beneficiary Private Keys
- Unencrypted key recovery shares

## 13. Failure and Edge Case Matrix

| Edge Case / Failure | System Behavior & Safeguards |
|---|---|
| **Corrupted Ciphertext / Modified Tag** | AES-GCM decryption throws authentication tag mismatch error. Client halts processing and flags asset as `TAMPER_DETECTED`. |
| **Invalid Beneficiary Public Key** | Web Crypto `importKey()` fails. Server rejects public key registration attempt. |
| **Lost Beneficiary Private Key** | Beneficiary cannot unwrap DEK upon trigger. User must execute key replacement workflow while active. |
| **Failed Fingerprint Verification** | Public key marked `REJECTED`. Server blocks DEK wrapping for this key. |
| **Beneficiary Revocation** | Triggers DEK rotation flow. Asset re-encrypted with new DEK; old wrapped DEK purged. |
| **Interrupted Key Rotation** | Database transaction rolls back. Asset remains in `SAFE HOLD` until rotation re-runs. |
| **Duplicate Public Key Registration** | Backend rejects duplicate public key fingerprints per tenant. |
| **Tampered Wrapped DEK** | Asymmetric unwrapping fails on beneficiary client with cryptographic decryption error. |
| **Unavailable Beneficiary** | Asset remains securely encrypted. Beneficiary receives payload package when online post-trigger. |
| **Unavailable User** | Liveness threshold breaches; staged warning machine advances to trigger state; wrapped DEKs delivered to verified beneficiaries. |

## 14. Security Requirements Summary

1. **Secure Randomness**: All DEKs, IVs, and salts must be generated using `window.crypto.getRandomValues()`.
2. **Key Separation**: Unique DEK per asset; unique KEK per user; unique key pair per beneficiary.
3. **Private-Key Confidentiality**: Beneficiary private keys must never leave beneficiary local devices.
4. **Authenticated Encryption**: All asset payloads must use `AES-GCM-256` with 128-bit authentication tags.
5. **Out-of-Band Beneficiary Authenticity**: Fingerprint comparison mandatory before trusting public keys.
6. **Cryptographic Revocation**: Revocation must trigger DEK rotation and re-encryption.
7. **Tamper Resistance**: Tampered ciphertext or wrapped keys must fail safely without disclosing plaintext.
